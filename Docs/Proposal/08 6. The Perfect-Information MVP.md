# 6. The Perfect-Information MVP

A deterministic research executable that turns Sparrow nests into chronological material decisions.

![[Attachments/image4.png]]

*Figure 4. Validation architecture. The baseline and oracle share geometry, candidate sets, remnant accounting, and benchmark streams; only the future-information policy differs.*

## 6.1 System boundary

The system begins with a chronological order stream and an initial inventory. At each event it generates candidate nests for compatible stock, extracts resulting remnants, invokes a policy, executes the selected action virtually, updates inventory, and advances time. The same stream is replayed under every baseline and oracle policy. All randomness is seeded and all candidate sets are persisted so comparisons are paired and reproducible.

## 6.2 Canonical domain model

| Entity | Minimum fields for validation |
| --- | --- |
| Part | ID, exact polygon, quantity expansion, allowed rotations, clearance, order link. |
| Order event | ID, timestamp, due status, released batch, part instances, hidden/revealed status for each policy. |
| Stock piece | ID, exact outer polygon, full-sheet/remnant flag, parent stock, acquisition cost, creation time, metadata placeholders. |
| Placement | Part ID, stock ID, rotation, translation, solver provenance. |
| Candidate nest | Stock choice, placements, current cost, solver seed/configuration, raw residual geometry, retained remnants. |
| Inventory state | All current full sheets/remnants, cumulative purchases, scrap, storage state, and provenance chain. |
| Decision event | Policy, information set, candidate archive, chosen action, rejected alternatives, cost accounting. |

## 6.3 Sparrow candidate factory

Sparrow is selected because it is open source, reproducible through seeds, and designed for high-quality irregular 2D strip packing. [1] Its strength makes the test rigorous: YieldForge must find future value among layouts generated by a solver already optimized aggressively for current compaction.

The adapter will not request one answer. It will capture multiple feasible incumbents from progressive runs, execute multiple deterministic seeds, and retain solutions inside an immediate-cost envelope relative to the best myopic layout. The initial envelope grid will include 0%, 0.1%, 0.25%, 0.5%, 1.0%, and 2.0%. The system will report how much candidate topology diversity emerges at each sacrifice level.

Sparrow solves strip packing rather than a generic fixed-bin objective. The adapter will set the strip width to the standard sheet width, determine the best occupied length, retain layouts within epsilon, and reject layouts that exceed the fixed sheet length. For irregular remnants, the system will call jagua-rs or a thin custom optimizer because jagua-rs supports irregular containers and separates geometric feasibility from the optimization strategy. [2]

### CANDIDATE DEDUPLICATION

Candidate count is not a useful diversity measure if the residual states are equivalent. The archive will deduplicate candidates using connected-component count, largest component area, minimum width, aspect ratios, edge accessibility, convexity, raster or distance-transform signatures, and fit against a representative set of future shapes. The full exact polygons remain the source of truth.

## 6.4 Exact remnant extraction

For each candidate, the geometry engine subtracts buffered placed parts and process loss from the stock polygon. The connected components of the residual form theoretical leftover regions. Each region is then classified as retained remnant or scrap according to minimum area, minimum width, bounding dimensions, connectivity, and an optional edge-access rule.

| Geometric accounting<br>Unused = Stock minus union(buffered placed parts) minus forbidden zones<br>RetainedRemnants = eligible connected components(Unused)<br>Scrap = Unused minus RetainedRemnants |
| --- |

Every nest must satisfy the accounting invariant: stock area approximately equals placed-part area plus retained-remnant area plus scrap plus modeled process loss. Tolerances will be explicit. Any violation fails the run because a small geometric accounting bug can manufacture a false economic advantage over thousands of orders.

## 6.5 Remnant-as-stock feasibility

A retained remnant becomes an irregular container available to later orders. The fit engine first applies cheap compatibility and size filters, then performs an exact placement search. Successful use produces a placement set and a new residual polygon, preserving the full parent-child provenance chain. This recursive capability is the physical core of the experiment: a remnant is valuable only if future demand can actually consume it.

The exact fit oracle will be exposed independently from the policy layer. This prevents policies from using area or bounding-box approximations as ground truth and allows geometry tests to be verified separately from economic tests.

## 6.6 Deterministic chronological simulator

1. Initialize the standard-sheet supply, any starting remnants, fixed cost parameters, and a timestamped order stream.

1. Reveal only information permitted to the active policy at time t.

1. Enumerate compatible current stock pieces and generate or retrieve cached candidate nests.

1. Extract retained remnants and the full resulting inventory state for every candidate.

1. Ask the policy to select an action and persist its rationale and candidate scores.

1. Virtually execute the cut, update purchased material, scrap, retained inventory, storage age, and provenance.

1. Advance the clock, reveal the next event, and repeat until the closed evaluation horizon ends.

1. Liquidate or conservatively value ending inventory according to the pre-registered terminal rule.

Identical input events, geometry versions, policies, and seeds must produce byte-equivalent decision logs or a formally defined canonical equivalent. Event sourcing will make every policy difference auditable.

## 6.7 Strong baseline suite

The final comparison will use the strongest baseline, not the easiest baseline to beat. Candidate policies include:

- Best immediate Sparrow utilization on a new sheet.

- Remnant-first, smallest-sufficient-stock selection.

- Largest/oldest remnant first to reduce inventory congestion.

- Best-fit policy minimizing immediate residual area.

- Regular-remnant heuristic favoring one large edge-accessible component.

- Current released-order co-nesting and known-order lookahead.

- Composite policy selected on a separate calibration set, then frozen before final evaluation.

The baseline and oracle will share the same candidate sets and stock eligibility rules in the primary analysis. A secondary expanded-search analysis will separately measure whether candidate generation is the bottleneck.

## 6.8 Oracle A: perfect-future rollout

For every current candidate, Oracle A executes the candidate and then replays the complete realized future using the strongest deterministic baseline. It chooses the current candidate with the lowest total downstream cost. This is a one-step policy-improvement method: future demand is known, but future decisions are not globally reoptimized.

| Oracle A<br>Q_rollout(candidate_t) = CostNow(candidate_t)<br>+ CostOfActualFuture under frozen strong policy<br>Choose candidate_t with minimum Q_rollout |
| --- |

Oracle A is computationally manageable, interpretable, and likely sufficient to reveal whether residual geometry has option value. It is not the strongest possible clairvoyant policy.

## 6.9 Oracle B: beam-search perfect-information policy

Oracle B expands multiple candidate decisions at every event and retains a beam of materially distinct inventory states. State hashing, cost bounds, inventory dominance, and candidate caching control the combinatorial growth. Beam width and compute budget will be reported with every result.

Dominance is conservative. One state can eliminate another only when it has no higher incurred cost, fulfills the same demand, and its remaining inventory is demonstrably at least as useful under an exact or safely relaxed comparison. Approximate geometry similarity may be used for beam diversity but not to assert strict dominance.

### EXACT VALIDATION ON SMALL INSTANCES

Small order streams with limited candidates will be enumerated exhaustively. The gap between exact search and beam search establishes whether the scalable oracle is strong enough to support a go/no-go decision. If the approximation gap is large or unstable, the project cannot responsibly interpret the measured oracle savings as the opportunity ceiling.

## 6.10 Cost accounting

| Cost component | Validation treatment |
| --- | --- |
| New stock purchase | Full acquisition cost when a standard sheet is opened; no area-prorated fiction unless the benchmark explicitly models it. |
| Scrap proceeds | Credited only when material is actually scrapped, at a conservative fixed value. |
| Storage | Per-remnant or area/time cost charged while material remains in inventory. |
| Handling | Fixed touch cost when a remnant is returned to stock or retrieved for cutting. |
| Process loss | Fixed kerf/clearance model applied identically to all policies. |
| Terminal inventory | Primary result uses conservative liquidation at scrap value or zero incremental option credit; sensitivity includes alternate treatments. |

Every published result will include the Sparrow commit, jagua-rs version, benchmark generator version, stream seed, solver seeds, epsilon, candidate budget, remnant rules, policy configuration, beam width, terminal treatment, and source hashes. Candidate archives should be cached so policy comparisons never silently receive different action sets.

## 6.13 Explicit non-goals

- No web application, production database service, Kubernetes deployment, authentication, or customer dashboard.

- No neural network, reinforcement learning, demand forecast, quote-conversion model, or learned value function.

- No machine postprocessor, NC code, cut-sequence optimization, thermal model, or certification workflow.

- No heterogeneous strength or quality fields beyond reserved schema placeholders.

- No multi-machine dispatch, order waiting, purchasing optimization, or shop-floor control.

- No claim that the scalable oracle is a mathematical upper bound without exact proof.
