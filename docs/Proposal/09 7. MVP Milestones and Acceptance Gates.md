# 7. MVP Milestones and Acceptance Gates

The MVP is divided into four independently reviewable phases. Each phase produces a usable research artifact and has an explicit acceptance gate; later phases are not assumed to proceed automatically.

![[Attachments/image5.png]]

*Figure 5. Four-phase perfect-information MVP. Detailed acceptance criteria and kill gates appear in the milestone table below.*

| ID | Milestone | Primary deliverable | Acceptance gate |
| --- | --- | --- | --- |
| M0 | Experiment specification and invariants | Frozen scope, metrics, information sets, cost rules, terminal treatment, and benchmark manifest format. | No ambiguous policy information or cost accounting remains. |
| M1 | Canonical schemas and geometry round-trip | Part/order/stock/remnant/placement/state schemas; exact import/export tests. | Geometry survives transformations within declared tolerance. |
| M2 | Sparrow candidate harness and archive | Pinned adapter, multi-seed runs, progressive incumbent capture, epsilon filters, reproducible candidate store. | At least one benchmark yields a stable population of materially distinct near-optimal residual states. |
| M3 | Remnant extraction and accounting | Exact connected residuals, eligibility filters, scrap classification, area reconciliation, visual fixtures. | All accounting invariants pass across adversarial geometry tests. |
| M4 | Irregular remnant reuse and fit oracle | Future parts nested into irregular remnants; recursive residual creation; provenance tracking. | Favorable toy sequence demonstrably avoids a new sheet through exact remnant reuse. |
| M5 | Deterministic chronological simulator | Event sourcing, inventory mutation, storage/scrap accounting, replay logs, cached actions. | Identical manifests produce identical decision histories and totals. |
| M6 | Strong baseline policies | Myopic, remnant-first, best-fit, aged-remnant, regularity, current-pool, and known-order policies. | Baseline selection is frozen on calibration data before final evaluation. |
| M7 | Perfect-information rollout oracle | Current-action rollouts through the realized future with paired candidate sets. | Hand-verified toy cases and monotonic sanity tests pass. |
| M8 | Beam-search oracle and exact checks | State hashing, pruning, beam diversity, exhaustive small-instance reference. | Approximation gap is quantified and acceptable for decision use. |
| M9 | Benchmark generator and sensitivity plan | Static geometry ingestion, temporal regimes, controls, seeds, and parameter grid. | No-signal and high-recurrence controls behave in the expected direction. |
| M10 | Experiment execution and verdict | Paired results, confidence intervals, ablations, failure analysis, go/no-go report. | Decision issued under the pre-registered threshold without post-hoc threshold changes. |

## 7.1 Phase A - Foundation

Phase A freezes the experiment, establishes canonical geometry, and turns Sparrow into a reproducible candidate source. It ends before the more difficult remnant inventory and simulator work. The review artifact is a set of candidate nests and residual-state visualizations generated from immutable manifests.

| Kill gate A<br>Stop if geometry cannot round-trip reliably, Sparrow cannot be instrumented within the allotted time, or deliberately favorable layouts fail to produce meaningfully different residual states. |
| --- |

## 7.2 Phase B - Physical core

Phase B creates exact remnants, reuses them as irregular stock, and replays a chronological inventory. This phase must prove the physical mechanism before any oracle algorithm is trusted.

| Kill gate B<br>Stop if material accounting does not reconcile, remnant-as-stock placement is unstable, or identical replay manifests do not produce identical histories. |
| --- |

## 7.3 Phase C - Oracle

Phase C establishes strong baselines and two perfect-information policies. The rollout oracle provides a tractable signal; beam search tests whether long-horizon interactions materially increase value. Exhaustive small instances validate search quality.

| Kill gate C<br>Stop or redesign if the scalable oracle is materially weaker than exact search on tractable cases, if the result depends on a strawman baseline, or if runtime prevents a meaningful benchmark sweep. |
| --- |

## 7.4 Phase D - Evidence

Phase D generates the controlled temporal dataset, runs the sensitivity and ablation matrix, and issues the investment decision. The final report must include negative controls and failure modes, not only favorable regimes.

| Final gate<br>Proceed beyond the oracle only if net incremental savings clear the threshold against the strongest baseline and survive conservative remnant, storage, terminal-value, and search-quality assumptions. |
| --- |

## 7.5 Program outputs

- A versioned open-source dependency manifest and reproducible research repository.

- Canonical schemas for exact parts, stock pieces, remnants, candidate nests, and inventory events.

- A Sparrow candidate archive with topology-aware diversity measures.

- An exact remnant extraction and irregular reuse engine.

- A deterministic chronological simulator and baseline policy suite.

- Perfect-information rollout and beam-search policies with exact small-case validation.

- A public-geometry-based synthetic temporal benchmark suite.

- A final decision report explaining whether value exists, where it exists, and what limits it.
